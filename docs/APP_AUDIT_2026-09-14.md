# Content Studio 1.2.92: application audit

Date: September 14, 2026. Scope: current working tree and the existing Windows
1.2.92 installer. This was a read-only audit of production code and live data.
Only this report and an isolated reproduction script were added. No articles,
Pins, Meta posts, credentials, application settings, or installed versions were
changed. No live publication or destructive security testing was performed.

## Findings

### 1. P1: Publishing to another WordPress site can overwrite an unrelated post

Evidence: [main.js:9182](<C:/Users/lenovo/Documents/New project/electron/main.js:9182>)
and [ArticleEditor.jsx:642](<C:/Users/lenovo/Documents/New project/src/components/ArticleEditor.jsx:642>).

The editor passes the article's previous wordpressPostId when another site is
selected. The backend prefers that unscoped ID over its site-specific receipt.
An article previously published as post 42 on site A is sent to the update
endpoint for post 42 on site B. If B has a different post with that ID, its
content can be overwritten. If B returns 404, the fallback creates a new post,
which can hide the defect during ordinary testing.

Reproduced with the actual publication handler and mock HTTP: the destination
was https://site-b.example/wp-json/wp/v2/posts/42 despite the article's existing
URL belonging to site A.

Fix: persist publication identity per normalized site URL and article ID.
Only reuse a post ID after confirming its owning site and article marker.
Store category selections per site too; numeric category IDs are site-local.
Test two sites with colliding post and category IDs.

### 2. P1: Failed WordPress updates can be reported as successful

Evidence: [main.js:9130](<C:/Users/lenovo/Documents/New project/electron/main.js:9130>)
and [main.js:9292](<C:/Users/lenovo/Documents/New project/electron/main.js:9292>).

After a rejected update, reconciliation accepts an existing publication
receipt without fetching the current remote content. That receipt proves only
that an earlier publication existed, not that the latest update succeeded.
The handler then returns success, allowing the UI to record publication of
changes WordPress did not accept.

Reproduced with an existing receipt and HTTP 403 on the update: one rejected
POST was made, no successful update occurred, but the handler returned success.

Fix: separate create reconciliation from update reconciliation. Definitive
rejections must remain failures. For ambiguous update outcomes, verify the
requested revision/content hash remotely before claiming success. A cached
post ID is not an update receipt.

### 3. P1: Settings corruption recovery can roll back healthy article data

Evidence: [main.js:323](<C:/Users/lenovo/Documents/New project/electron/main.js:323>)
and [workspace-store.js:153](<C:/Users/lenovo/Documents/New project/electron/workspace-store.js:153>).

Repairing an invalid config.json copies a full workspace backup into that file.
The subsequent migration unconditionally writes any embedded workspace roots
over the SQLite database, even if that database is healthy and more recent.
This can discard new articles, edits, Pins, receipts, and other newer records.

Reproduced against temporary SQLite: a healthy two-article collection with a
new edit was replaced with the one stale article from a restored settings
snapshot. The newer article and edit disappeared from the active collection.

Fix: distinguish first-time migration from settings-only recovery. Migrate a
workspace root only when its authoritative database data is absent, unless
the user explicitly requests whole-workspace restoration. Preserve a snapshot
of both stores before any recovery and test mixed-age config/database states.

### 4. P1: Production dependencies include known vulnerable versions

Evidence: current npm audit --omit=dev reports five affected packages: three
high and two moderate; zero critical by the registry's classification. The
full dependency tree reports ten affected packages, including build tooling:
five high, three moderate, and two low. These counts do not prove that all
advisories are exploitable through this app.

| Package | Installed | Patch target / action | App-specific assessment |

| sharp | 0.35.3 | 0.35.4 or newer compatible patch | The app decodes downloaded images before final validation. No HEIF decoder block is configured. The vendor describes libheif issues and possible RCE under particular glibc Linux conditions; Windows RCE was not established here. |
| fast-uri | 3.1.5 | 3.1.6 or newer compatible patch | Comes through electron-store/conf/Ajv. The app's outbound URL guards use native URL parsing; an outbound SSRF exploit through this dependency was not demonstrated. |

| sanitize-html | 2.17.6 | Upgrade to a release outside the affected range | Current WordPress tag allowlists exclude SVG/SMIL, reducing exposure to the reported bypass. No renderer XSS was demonstrated. |

and run import, sanitizer, image, update, and packaged-startup tests. Do not run
a blind force-upgrade across major versions. Prioritize the image decoder
because untrusted media reaches it in normal workflows.

### 5. P2: Meta can reuse an outdated crop after a Pin is regenerated

Evidence: [meta-auto-pack.js:197](<C:/Users/lenovo/Documents/New project/electron/meta-auto-pack.js:197>)
and [main.js:6914](<C:/Users/lenovo/Documents/New project/electron/main.js:6914>).

Crop compatibility checks dimensions, source kind, and Pin ID, but not the
source image path, hash, or revision. Regenerating the same Pin ID changes its
image while leaving an old 4:5 Meta crop eligible for reuse. Bulk preparation
then skips resizing because it sees an already complete image asset.

Reproduced using automaticMetaProject: the source library pointed at the new
Pin image, while imageAssets still referenced OLD-CROP.jpg.

Fix: bind each resized asset to a source fingerprint plus crop parameters.
Invalidate it on image replacement, including featured-article images. Test
regeneration that preserves the Pin ID and replacement at the same URL.

### 6. P2: GHL duplicate prevention changes when a schedule expires

Evidence: [main.js:2440](<C:/Users/lenovo/Documents/New project/electron/main.js:2440>),
[main.js:2891](<C:/Users/lenovo/Documents/New project/electron/main.js:2891>), and
[main.js:7298](<C:/Users/lenovo/Documents/New project/electron/main.js:7298>).

Direct upload first moves old/near-term dates to future slots, then hashes the
entire resulting payload for deduplication. Retrying the same original rows
later changes the schedule and therefore the lookup key. A previous successful
or unknown-outcome receipt can be missed, allowing another create request.

Reproduced with actual normalization, payload, and fingerprint functions:
identical input rows produced different keys before and after date expiry.
The changed key cannot match the earlier receipt in priorGhlReceipt.

Fix: persist a delivery/attempt ID and normalized schedule before the first
request. Resolve the existing outcome before rescheduling. A deliberately new
post should be an explicit new delivery, not an accidental date-based retry.

### 7. P2: The distributable Windows installer is unsigned

Evidence: Get-AuthenticodeSignature on release/Content Studio Setup 1.2.92.exe
returned NotSigned. The generic packaging log's signing step is not proof of
a successful publisher signature.

Fix: configure a trusted Windows code-signing identity, timestamp the installer
and executables, verify signatures after packaging, and fail distribution
builds when the signature check fails. This needs a signing certificate or
signing service. Obfuscation and ASAR integrity do not authenticate the source
of an installer and cannot make shipped JavaScript impossible to extract.

## Important limits

No claim is made that every app path is error-free. This is not a penetration
test or a live audit of your WordPress/Pinterest/GHL accounts. Paid AI generation,
remote publication, live platform scheduling, and hostile media exploitation
were not performed. No new local Pinterest CSV truncation was reproduced; the
20-Pin single-file regression passes. Pinterest's original generic import
failure still cannot be attributed to a specific host or account from its email.

## Recommended order

1. Fix cross-site WordPress post identity and false update success.
2. Make settings recovery preserve healthy SQLite data.
3. Update vulnerable dependencies and verify a rebuilt installer.
4. Add source fingerprints to Meta crops and stable GHL delivery IDs.
5. Sign distribution builds and make signature checks mandatory.
6. Promote these probes into regression tests that assert correct behavior,
   then add controlled staging-site tests for publishing and failed retries.
